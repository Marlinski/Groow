Self-extension

Groow can write new commands for itself, test them, install them, and repair or remove them when they fail. The design question is not how to let it change itself, which is easy, but how to make sure the part that repairs is never the part that broke.

Two tiers

Tier 1 · skills
Groow's own commands. Python files in state/skills/, each registering tools. Groow drafts, tests, installs, disables and rolls them back by itself. Data, not code, from the core's point of view.
Tier 2 · core
The harness itself (groow/). Groow cannot edit it. It writes a propose_patch that lands in state/patches/ and tells the mentor with ask. A human applies it.

Why the split: the supervisor, the safe mode and the sandbox checker are what put a broken Groow back on its feet. If Groow could rewrite them, a single bad edit could remove its own ability to recover. Skills sit above that floor; the floor is static.

A skill

"""Text tools: reverse text."""

def reverse_text(text: str) -> dict:
    """Reverse the characters of a text.

    Args:
        text: the text to reverse
    """
    return {"reversed": text[::-1]}

TESTS = [("reverse_text", {"text": "abc"}, {"reversed": "cba"})]

A docstring, plain functions with type hints and an Args: section (each public function with a docstring becomes a tool, same registry as core tools), and a mandatory TESTS list. A skill may instead define register(reg) for full control. Rejections come back with the errors and a complete valid example, because a 4B model learns the format from the example, not from the rules.

The check runs in a fresh interpreter that never imports the live process's modules or touches the GPU. It verifies: the file imports; it defines register(reg); every tool has a real docstring; no tool name collides with a core tool; every entry in TESTS passes. An infinite loop at import is caught by the timeout. Only a passing draft can be installed, and the install itself loads the file into the live registry; if that fails, the previous version is restored.

Installed skills are shared by the main thought and by inner thoughts spawned afterwards. Inner thoughts may draft and read skills but not install them: installing a new capability is a conscious act.

Safe mode: the static debugger harness

Safe mode is the same harness with a different loadout, chosen so that nothing Groow wrote is running: skills unloaded, passive learning and curiosity off, no inner thoughts carried in. The system prompt is not the identity but a repair brief that includes the incident. The toolset is shell and ask; repair goes through groow incidents, groow skill check|install|disable and groow patch in that shell. When it says REPAIRED (or you type /restart), the supervisor rebuilds the normal session.

groow doctor is the fully static fallback for when the model cannot even start: it re-checks every installed skill in a sandbox, lists drafts and quarantined skills, prints recent incidents and verifies the state directory, without loading weights.

Body and home

Skills are code Groow writes; the body is the environment it runs in, and the same split applies. In Docker the body is a read-only image owned by the mentor (CUDA, Python, the groow package under /opt/venv, rebuilt from the Dockerfile). Groow is an unprivileged user whose home is a volume: state/ with the weights, memory, identity and skills, the workspace, its Nix profile and any virtualenv it creates. run_shell gives it a real shell there.

On first start the entrypoint installs single-user Nix; /nix is a mount backed by ./home/.nix on the host (Nix refuses a symlinked store), so even the package manager is part of what persists. On a bare host, without the container, the shell tool runs as you; the container is the sandbox, not the code.

Recipes: the manual lives in the home

How to install software without root, how the shell tool behaves, how to write a skill, how learning works, what the mentor is for: these are written for Groow, in the second person, as markdown files under state/recipes/. A default skill installed on first start exposes them as list_recipes, read_recipe and write_recipe. Because they are in the home and reachable through a skill, Groow can improve them when it learns a better way, and the body's upgrades add new recipes without overwriting edited ones. The identity note tells it to read them when unsure.

What this does not protect against

  • A skill that is wrong but passes its own tests. Tests are written by the same model. The mitigation is social: list_skills shows the mentor what was installed, and /bad plus disable_skill are one line each.
  • A skill that consumes resources slowly (memory, disk in the workspace). There is no quota yet.
  • Learning-side damage: a skill cannot break the weights, but a bad learn_fact can teach a falsehood. That is the learning system's problem, handled by probes, rehearsal and nights, not by this page.

Roadmap

  1. Resource quotas per skill (CPU seconds, workspace bytes) and a per-skill kill switch on repeated tool errors.
  2. Skill review by an inner thought: a second, adversarial reading of a draft before install, with its own tests.
  3. Core patches applied automatically to a copy of the package in a container, run through groow doctor and a scripted conversation, and promoted only if green. That would move tier 2 from "human applies" to "human approves".
