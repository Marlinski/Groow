Daemon and UI

Groow runs as one process that owns the GPU and the state. Everything else, the fullscreen UI, the line client, a script, a future web page, is an HTTP client. Single queries are plain HTTP, the run loop streams as Server-Sent Events, and interactive UIs use a WebSocket.

The protocol

Base URL http://127.0.0.1:7373 (api_host, api_port in groow.json; the daemon also writes it to state/groow.url). JSON everywhere.

RouteUse
GET /hellobirth card, identity, model, tools, status, inbox
GET /statuslive snapshot
POST /ask {"text"}single query: queues the message at USER priority and waits for that turn; returns final, tools_used, seconds and the turn's events
POST /say {"text"} · POST /command {"text"}enqueue and return at once (req correlation id in the reply and on the turn's events)
GET /events?replay=NServer-Sent Events stream of the run loop: hello, the last N events flagged replay, then live; keepalive comments every 15 s
WS /ws?replay=NWebSocket for UIs: same events out, one JSON object per message; in: {"cmd":"say"|"command"|"status","text":…}
curl -s localhost:7373/status | jq .mood
curl -s -X POST localhost:7373/ask -d '{"text":"what is 17*23?"}' | jq .final
curl -N localhost:7373/events            # watch it live

Both streams carry the same event objects. Events are produced from several threads inside the daemon (the GPU executor emits learned, tools emit progress), so emission hops onto the event loop and fans out through one queue per connection; a client that stops reading is dropped rather than slowing the mind.

EventPayloadMeaning
hellobirth, identity, model, tools, status, inboxfirst message to a new client, followed by the last 120 events (replay: true)
statusmood, steps, nights, rank, thoughts, queue, server stats, gpu, skillsevery 2 s
turn_start / text / turn_endwho (user or signal), kind, text; streamed deltas; final text, tools usedthe main thought handling one signal
tool_call / tool_resultname, args, result, actor (main or thought:id)from the main thought and from inner thoughts
learnedloss, tokens, step, probethe passive gradient step after a turn
thoughtevent (spawn, step, focus, done, paused, resumed, killed), id, status, goal, steps, textinner-thought lifecycle
sleepphase (start, progress, done), outcome, probes, identity lossesa night
inbox, log, byequestions for the mentor; anything else; shutdown

Mood is derived by the daemon from the event stream (thinking, speaking, tooling, learning, reading, dreaming, sleeping, repair, idle) and carried in status. It is what the creature animates.

The UI

Left, the conversation: your messages in amber, Groow's in phosphor mint streamed as they arrive, signals from inner thoughts and the idle impulse in violet, tool calls in sky blue, learning steps dimmed. Right, the creature (a sprout, because Groow grows), the identity card, and the inner thoughts with their live status. Bottom, one status line: mood, queue, running thoughts, generation batches and preemptions, GPU memory, learning on or off.

The identity card is the birth certificate: id, birth time, age counted live to the second, lineage (base model), body (GPU), mentor, plus what has changed since: identity version, nights, steps, skills. It comes from state/birth.json, written once at groow init, read-only on disk, and Groow has no tool that writes it. The self-description in identity.md is what Groow thinks it is; the certificate is what it is.
